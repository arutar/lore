История по версиям — `platform/docs/releases/`. Коротко:

- 0.2.6 — анонимный clone публичного репозитория;
- 0.2.7 — push как операция на сервере (опрос статуса вместо одного запроса, который обрывался через 50 с);

- 0.2.9 — журнал push без принудительного сброса на диск (конец коммита из GUI быстрее на ~16 с), клиент повторяет `Start`, если сервер потерял операцию;
- 0.2.10 — просмотр изменений ревизии в WebUI (панель справа от истории, стрелки ← →, ссылка `?revision=`), API `/repositories/{id}/revisions/{sig}/changes` и `/summary`.
- 0.2.11 — скачивание клиента с главной (`/downloads/`, `clients.tsv` в бандле, `LORE_CLIENT_DOWNLOADS=online|offline|off`), темы v3.
- 0.3.0 — MCP для ИИ-агентов: `/mcp` в control plane, 9 инструментов только для чтения, токены `lore_mcp_…` (в базе SHA-256), переключатель MCP (личный сильнее группового), ссылки на скачивание на `LORE_MCP_LINK_TTL`, режимы `off|internal|on` в setup; мобильная вёрстка всех страниц. Руководство — `platform/docs/mcp.md`, решение — `platform/docs/decisions/0002-mcp.md`.

Замеры загрузки 703 009 файлов — в разделе Performance основного README.

## Цель

Простой аналог SVN на основе Lore: self-hosted сервер с WebUI, интеграция с Проводником Windows, работа во внутренней сети без интернета и во внешней сети, установка одной командой через Docker Compose. Вход через Keycloak: учётки Active Directory и локальные (email). Роли admin/user, права на репозиторий `none < read < write < owner`, приватные репозитории без права не видны. Windows-клиент — CLI, Companion и расширение Проводника; Linux — CLI (интеграция с файловыми менеджерами в работе).

## Состав

| Компонент | Что делает |
|---|---|
| Go control plane | WebUI API, сессии, права, аудит, обмен токенов для нативного клиента, gRPC для сервера Lore |
| PostgreSQL | две базы: `lore` (control plane) и `keycloak` |
| Keycloak 26.4 | вход OIDC, device flow, федерация AD, регистрация и письма; запускается в production-режиме |
| Сервер Lore | форк EpicGames/lore: хранилище, ревизии, блокировки (в файле `locks.json`, соблюдаются при push) |
| Caddy | единый вход HTTP/HTTPS; админка Keycloak и realm `master` закрыты |
| WebUI | React + TypeScript, вариант «Studio», русский и английский, 9 тем |
| Windows | C++ COM-расширение Проводника, C# Companion (WebView2), MSI на WiX |

## Реализовано и проверено

**Идентичность и права**
- Учётка AD определяется по `objectGUID` (атрибут `LDAP_ID` Keycloak, claim `ldap_id`), а не по виду имени. Переименование в AD не создаёт новую учётку; новая учётка с занятым именем вытесняет прежнюю, права по имени не наследуются.
- Группы AD, включая вложенные, читаются по `objectGUID`. Исключение из группы и отключение в AD доходят до WebUI и нативного клиента за `LORE_LDAP_REFRESH` (по умолчанию 5 минут). При недоступности AD известные группы действуют `LORE_LDAP_OUTAGE_GRACE` (8 часов), потом доступ по группам закрывается; локальные учётки входят без обращения к AD.
- Локальный `admin` всегда существует: `setup` создаёт его заново, если его нет или если имя занято учёткой из AD. Keycloak ищет свои учётки раньше AD, поэтому под именем `admin` входит только локальная. Если прежде администратором была AD-учётка `admin`, роль переходит к локальной.
- Первый администратор назначается один раз и только локальной учётке; учётка AD с именем `admin` роль не получает.
- Токены нативного клиента принимаются только выпущенные для Lore (`aud`) клиентами `lore-native` или `lore-control-plane` (`azp`). Регистрация репозитория через gRPC — только администратору или сервисной учётке.
- Анонимный clone — только для публичного репозитория, поиск по точному имени; приватный и несуществующий неотличимы (403).
- Права выдаются пользователям и группам с поиском по имени; подсказки — от 2 символов, не больше 10 пользователей и 10 групп. WebUI не даёт понизить или удалить последнего владельца; сервер это не запрещает, но администратор управляет любым репозиторием.
- Учётка AD, добавленная администратором, сразу хранится под логином из AD (атрибут входа), а не под почтой, даже когда realm регистрирует локальные учётки по почте; её находят по логину до первого входа.
- Аудит: права, пользователи, репозитории, настройки, вытеснение учётки; новые события сверху, постранично.
- Удаление репозитория (администратор, вкладка Settings, ввод полного имени): control plane просит Lore удалить репозиторий от имени администратора и удаляет свою запись только после подтверждения Lore. Если Lore не справился посередине, репозиторий остаётся в списке и удаление можно повторить; закрытие браузера удаление не прерывает (`internal/deletions`).

**Развёртывание**
- `setup.sh` / `setup.ps1`: случайные секреты в `.env`, без секретов в шаблонах. Повторный запуск применяет изменения публичного адреса, LDAP, SMTP и секрета сервисного клиента к существующему realm (`keycloak/configure-realm.sh`) — Keycloak импортирует файл realm только при первом старте.
- `LORE_DATA_ROOT` переносит все данные и сгенерированную конфигурацию; backup и restore берут его из `.env`.
- Готовые образы: при заданных `LORE_CONTROL_PLANE_IMAGE` и `LORE_SERVER_IMAGE` setup скачивает их вместо сборки (workflow `platform-images.yml` публикует их в GHCR).
- Backup: обе базы, хранилище Lore, ключ подписи, `.env`; архив доступен только владельцу, незавершённый backup не выглядит готовым, без хранилища или ключа backup отказывается выполняться.
- Restore: проверка контрольных сумм до остановки сервисов, восстановление в отдельный каталог, страховочная копия текущих баз, восстановление каждой базы одной транзакцией, откат при ошибке. Повреждённый архив отклоняется без остановки сервисов.
- Режим HTTP для внутренней сети: нативный клиент разрешает обычный HTTP к Keycloak на том же хосте, что и подключённый сервер Lore, без настройки на клиенте.
- Заголовки безопасности: CSP, `X-Frame-Options`, `nosniff`, Referrer-Policy, Permissions-Policy, HSTS при HTTPS.

**Блокировки**
- Блокировки хранятся в файле (`lore-server/src/plugins/file_locks.rs`, режим `file`), переживают перезапуск и попадают в backup; пакет блокировок ставится целиком или не ставится.
- Сервер отклоняет push, меняющий файл, заблокированный другим пользователем (`lore-server/src/hooks/lock_guard.rs`), с какого бы клиента он ни пришёл.
- Владелец или администратор репозитория снимает чужую блокировку в WebUI (вкладка Locks) с подтверждением и записью в аудит; блокировки пользователей, которые больше не могут войти, помечены.

**WebUI**
- Список репозиториев с поиском, подгрузкой и копированием адреса `lore://`; файлы, история, блокировки и скачивание через gRPC-сервисы Lore; доступ с поиском субъектов и отменой; пользователи с добавлением из AD; аудит; настройки темы, языка по умолчанию и регистрации; палитра команд Ctrl K; ширина от 390 px.
- Режим HTTP: браузер не даёт `crypto.randomUUID` и `navigator.clipboard` вне HTTPS и localhost. WebUI в таком случае создаёт ID репозитория через `crypto.getRandomValues` (`NewRepository.tsx`) и копирует через `execCommand("copy")` (`ui.tsx`). Других API, требующих защищённого контекста, в WebUI нет.
- Публичный репозиторий: переключатель «Все вошедшие пользователи» включён и недоступен — публичный доступ уже даёт чтение всем; собственное право сохраняется на случай, если репозиторий снова станет приватным.
- Вкладка Files: кто и когда последним менял каждый файл и папку (по `RevisionDiff` Lore, с правильной атрибуцией изменений, пришедших слиянием; кэш на репозиторий).
- Поиск и постраничный вывод на сервере для каталога, репозиториев и пользователей.
- Сеанс, истёкший при открытой странице: WebUI заменяет страницу сообщением «Войти снова» и после входа возвращает на ту же страницу (параметр `return`, только пути этого WebUI).
- Демо только для просмотра (`npm run build:demo`, `platform/web/src/demo`): настоящий интерфейс на выдуманных данных в браузере, изменения отклоняются, тема и язык запоминаются в браузере. Workflow `webui-demo.yml` публикует его на GitHub Pages, README ведёт на него кнопкой «Live preview». Обычная сборка демо-данных не содержит.

**Windows**
- Вход в новую учётку на тот же сервер заменяет прежнюю: старые учётные данные удаляются, повторно входить не нужно.
- Иконки команд меню Проводника — значок команды во весь размер, читаемый в 16 px; генератор `platform/windows/shared/svg/build-icons.mjs`, экспорт PNG/ICO — `export-icons.mjs`.
- MSI на WiX 7.0.1 (per-machine, регистрация COM, PATH), единая версия компонентов; сборка и smoke install/uninstall в GitHub Actions.
- Меню: Clone, Sync, Commit, Stage, Unstage, Revert, Resolve conflicts, Status, History, Lock, Unlock, Accounts.
- Companion не решает за пользователя там, где можно потерять работу: при staged-файлах и при файлах, изменённых и здесь, и на сервере, он останавливается до изменений, показывает список файлов и варианты; удаление своих изменений всегда подтверждается. Commit проверяет чужие блокировки до записи ревизии.
- Окно Commit показывает список того, что войдёт в ревизию: изменённые файлы выбранных путей и всё, что уже staged. Тип изменения показан цветом: полоска у края строки и цвет имени (новый — зелёный, изменён — жёлтый, удалён — красный и зачёркнут). Список сгруппирован по папкам: флажок папки отмечает или снимает всё внутри, включая вложенные папки, папку можно свернуть в одну строку. По умолчанию отмечено всё; файлы, заблокированные другими, помечены и не отмечаются. Коммитятся ровно отмеченные файлы, снятые с отметки staged-файлы снимаются со stage с сохранением изменений.
- Окно Commit показывает список сразу, без ожидания сервера; чужие блокировки текущей ветки (не других веток — сервер проверяет только ветку push) подгружаются следом и выключают свои файлы. Если коммит отклонён до записи, stage возвращается к тому, что пользователь отметил сам.
- После отправки окно Commit показывает, что делает сервер: этап проверки, число проверок и перезапуски, если они были.
- Рабочая копия на сетевой папке (`\\server\share\repo`): Lore сохраняет UNC-путь (`lore-revision/src/util/path.rs`), раньше клон молча создавался на диске C. Папка `.lore` скрывается сразу после клонирования.

**Проверки**
- Go: модульные тесты; тесты хранилища выполняются и на памяти, и на PostgreSQL (`TEST_DATABASE_URL`, в CI — сервис PostgreSQL); `go test -race` в CI.
- Сквозной тест `platform/deploy/test/e2e.sh`: setup → вход администратора через форму Keycloak → репозиторий и локальный пользователь → вход пользователя со сменой временного пароля → право → backup → изменения → restore → проверка состояния. В CI — `platform-e2e.yml`.
- На стенде с живым AD и Keycloak (2026-11-12): чистая установка и повторный setup, вход, поиск в AD, нативные clone/commit/push, исключение из группы, отключение в AD, недоступность AD, backup/restore, повреждённый архив, WebUI.
- Клиент на живой установке (`platform/windows/tests`, 2026-11-15, клиент 0.1.26): 22 сценария Companion со вторым пользователем, работающим параллельно, и 21 шаг через настоящее меню Проводника с проверкой значков — все проходят.
- Стенд `mega-claude` (Windows, Docker Desktop, HTTP на порту 8080, 2026-11-17): создание репозитория и копирование адреса `lore://` в WebUI работают.
- Клиент 0.2.2 на `mega-claude` (2026-11-17): clone пустого репозитория через Companion и через CLI на `\\rndvm01\shara`, `.lore` скрыта; Commit 6 из 7 файлов с сетевой папки, неотмеченный файл остался неотправленным. Тесты путей ядра — на Windows и Linux.
- Сервер Lore: модульные тесты хранилища блокировок (перезапуск, пакеты, 50 параллельных пользователей, сбой записи).
- Push-операции (`lore-server/tests/unit/grpc/revision/v1/push_operation.rs`): перезапуск зависшей проверки и отказ после трёх, повтор после «Slow down», отказ без повтора, вытесненный обработчик не меняет результат, 48 одновременных push, чистка журнала, повтор Start. Решение и альтернативы — `platform/docs/decisions/0001-push-operations.md`.
- CI: релиз публикуется (и образы в GHCR) только после Rust-тестов, smoke, интеграционных тестов, lint, проверок платформы и e2e; у задач есть тайм-ауты. Тест FUSE `warm_lookups_under_concurrent_writes_stay_within_budget`, повесивший unit-задачу на 6 часов, помечен диагностическим, как соседние.

## Не проверено и ограничения

- Публичный DNS и ACME — нужен внешний сервер с портами 80/443.
- Подпись релиза и WiX Burn (автоматическая установка WebView2) не реализованы.
- Windows даёт ограниченное число слотов overlay-иконок; при установленных OneDrive, Dropbox или TortoiseSVN значки состояния Lore могут не отображаться.
- Сетевая папка: Windows несколько секунд кэширует содержимое каталогов на SMB-шаре, поэтому файлы, созданные прямо перед открытием окна Commit, могут не попасть в его список (и в этот коммит); они появятся при следующем открытии. Повторного сканирования не делаем — решение 2026-11-17.
- Хранилище `remote` не умеет записывать пару (ветка и результат push), поэтому там push остаётся одним запросом с пределом `request_handler_timeout_seconds`; сервер пишет об этом предупреждение при старте.
- Прогресс проверки push Companion читает из события, которого нет в пакете LoreVcs 0.13.0, по раскладке `lore.h`; при смене пакета это место надо проверить (`ServerProgressEvent` в `LoreOperations.cs`).
- Нативный протокол использует порт 41337 (TCP и UDP); из внешних сетей он может быть закрыт.
- Установка на Linux-хосте проверяется сквозным тестом в GitHub Actions (Ubuntu); стенд — Windows с Docker Desktop.
- Образы сервера собираются только для linux/amd64.
- Сервер Lore — форк; изменения аутентификации предложены upstream в EpicGames/lore#278, до ответа maintainers переносятся вручную.

## Полезные команды

```powershell
# Установка и повторное применение настроек
platform/deploy/setup.ps1            # или sh platform/deploy/setup.sh

# Backup и restore
platform/deploy/backup.ps1
platform/deploy/restore.ps1 -Backup platform/deploy/backups/BACKUP_NAME

# Обновление Windows-клиента
platform/clients/Install-Windows.ps1 -AllUsers

# Проверки
cd platform/control-plane; go test ./...         # с TEST_DATABASE_URL — и на PostgreSQL
cd platform/web; npm run build
# Сквозной тест: только на тестовой установке, он выполняет restore
LORE_E2E=destroy-test-data bash platform/deploy/test/e2e.sh
```

Подробная архитектура и диаграммы: `platform/docs/architecture.md`.
